# Routing backend API

Run the service with `docker compose -f backend/compose.yaml up -d --build`. The public API listens on port `8787`; OpenTripPlanner stays on the private Compose network.

* `GET /health` verifies that the API process can query the loaded OTP graph. During graph loading or restart it returns HTTP 503 with `ROUTER_UNAVAILABLE`; it never reports healthy from the API process alone.
* `GET /api/places?q=union&date=2026-09-06` searches the local GTFS stop index. Empty queries return an empty list. A supplied date excludes only stops whose source feed has known calendar bounds outside that date, while unbounded source records remain visible with their honest `validity` state. Each source-backed stop includes a bounded `servingRoutes` list when the validated scheduled index has an exact stop or direct parent-child match. Those badges represent scheduled GTFS service only, not a live departure, vehicle position, arrival prediction, or service alert.
* `GET /api/stop-routes?stopId=<qualified-stop-id>&date=2026-09-06` resolves one published stop record and its date-exact scheduled route badges. The identifier must exactly match a qualified source stop ID or an explicit stable version-alias mapping. The endpoint does not use a route number, name, coordinate, nearby stop, or vehicle position to resolve a stop. It returns source-backed stop fields and scheduled route metadata only; it is not a departure or live-vehicle endpoint.
* `GET /api/routes?agency=ttc&q=finch&date=2026-09-06&limit=50&cursor=<cursor>` searches the local route catalog after calendar-aware alias selection. Results use stable natural route ordering and return `{routes,total,nextCursor,coverage}`. Pass the canonical bounded `nextCursor` to continue, or use a bounded non-negative `offset` for an equivalent deterministic page. A supplied date must be a real calendar date. `coverage` states the selected date plus exact, fallback, and unknown counts, while every route retains its own validity interval. Missing validity bounds are unknown, never claimed as exact. Every entry identifies its public agency, exact GTFS feed version, route ID, official short and long names, and validated six-digit GTFS colors when supplied. Missing or malformed GTFS colors are returned as `null`; the service never invents a route color. Adjacent feed versions sharing an agency and route ID resolve to the version valid for the requested date; an out-of-range request is reported as a fallback rather than silently presented as exact coverage.
* `GET /api/coverage` reports every feed in the active graph, its service calendar, digest, byte size, loaded state, indexed stop count, active trip counts for the graph-build date and the following 14 days, current-date availability, and explicit zero-service warnings.
* `GET /api/departures?stopId=<feed:stop>&timeRange=3600` reads departures. Scheduled values are Unix epoch seconds computed from OTP's `serviceDay` plus the scheduled offset. `predictedArrival`, `predictedDeparture`, and `realtime` are populated only when OTP matched a verified GTFS-RT update to the scheduled trip.
* `POST /api/plan` accepts `{from:{lat,lon},to:{lat,lon},dateTime:"2026-09-05T08:00:00-04:00",arriveBy:false,wheelchair:false,maxWalkDistance:2000,preference:"fastest",preferWashrooms:false}`. Preference may be `fastest`, `transfers`, `walking`, or `waiting`. When `preferWashrooms` is true, the service prefers boarding, transfer, and alighting points with officially confirmed transit facility washrooms among trips within 20 minutes and 1,000 metres walking of the fastest eligible trip. It never treats nearby cafes, malls, parks, or unverified public washrooms as transit facilities and never promises a facility is open. Verified municipal washrooms use their separate arrival-time availability contract.

JSON bodies are limited to 32 KiB, coordinates must be finite numbers, OTP calls have a 15 second deadline, and returned legs are discarded when they lack valid endpoints. Upstream failures return one bounded public message without internal URLs or raw upstream details. No route or departure is synthesized locally.

Transport or router restart failures return HTTP 503 with `ROUTER_UNAVAILABLE`. A successful search with no itinerary returns HTTP 200 with an empty itinerary list and graph-bound `coverage.unavailableAgencies` for the selected date. Next service dates are selected from chronologically sorted calendar keys. The backend does not infer a required agency from coordinates, because a regional trip may use another operator.

The plan query uses OTP 2's documented `planConnection(origin, destination, dateTime, first, modes, preferences)` operation. Each leg includes string route and agency names, distance in metres, duration in seconds, and encoded polyline geometry. Each itinerary includes total distance, confirmed transit facility washrooms, the preference decision, and graph-bound provenance for the exact feed snapshot consumed by the running graph. See the [official planConnection reference](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/queries/planConnection). GTFS and OpenStreetMap data are loaded by the OTP deployment, while the generated `data/stops.json` provides ranked offline stop search.

Transit legs also include OTP's exact namespaced `tripId`, `routeId`, and `agencyId`, plus `agencyFeedId` derived only from the namespaced GTFS identifier. Clients can join a live vehicle to a planned leg without guessing from route names or destination text. Place search collapses only records with the same normalized name, agency, and exact finite coordinates; same-name stops at distinct coordinates remain independently selectable.

OTP applies verified GTFS-RT trip updates for MiWay and HSR every 30 seconds and alerts every minute. Exact trip ID validation matched 239 of 239 current MiWay updates and 182 of 182 current HSR updates to their respective static feeds before activation. Burlington's endpoint is healthy, but its current 103 trip IDs matched zero static trip IDs, so it remains status-only rather than corrupting scheduled routing. Other agencies remain scheduled unless their official live source and static identity join are both verified.

Current-date TTC coverage is restored using the independently validated archived official July 26 to September 5 timetable alongside the next September 6 to October 31 timetable. The running graph reports 32,874 active TTC trips for September 5, 2026. Four public smoke requests on that date returned 33 complete itineraries across TTC, York Region Transit and UP Express. Burlington still reports zero trips for September 5; the backend exposes that agency-specific gap without treating it as a service closure. TTC realtime updates remain separate from schedule coverage: mismatched static/live trip identifiers cannot establish an exact assignment.

Before a scheduled refresh downloads or rebuilds anything, it verifies every active graph feed version, manifest digest, and archive digest against the root feed snapshot. A missing version, changed manifest digest, missing archive, or changed archive stops the refresh before feed mutation or graph construction and retains the active graph. Promote a complete validated archive snapshot before refreshing; do not regenerate indexes from an older root feed directory.

GO and UP Express live feeds require a registered Metrolinx API key. The deployment reads it from a mode-600 host file mounted read-only into the API container. An internal proxy adds the key only to the outbound request and exposes credential-free Compose-network URLs to OTP on port 8788. That port is not published on the host. The proxy refuses redirects, bounds response time and size, caches briefly, and returns no upstream body or credential detail on failure. Install the key by piping it through standard input to `backend/install-metrolinx-key.sh`; never place it in an argument, environment variable, repository file, log, or OTP URL. GO and UP updaters remain disabled until their returned trip IDs are verified against the exact loaded static feeds.

`GET /api/integrations/status` reports a bounded Metrolinx summary: configured presence, GO and UP capability names, live/waiting state, last successful fetch timestamps, and protobuf entity counts. It never returns the credential, its properties, or a credential-bearing upstream URL. GO activation requires an exact live-to-static identity match; the activation sample matched 150 of 150 TripUpdate IDs. UP activation matched 5 of 5. OTP applied 153 of 153 GO and 5 of 5 UP updates on the first production poll. Metrolinx alert feed health is reported, but the alerts are not applied to OTP because current payloads contain blank mandatory entity IDs rejected by OTP 2.9.

`GET /api/vehicles/metrolinx?agency=go|up` returns the official GTFS-RT vehicle-position protobuf through a fixed allowlist. It accepts no arbitrary URL, never exposes the registered key, bounds retrieval, and returns `VEHICLE_DATA_UNAVAILABLE` without raw upstream details. Vehicle descriptors and trip IDs remain exactly as published so the consuming service can join them to planned `tripId` values.
